## 6. 缺陷 Q2-BUG-001：消息成功但回执丢失，重试产生重复消息

严重度建议：中；修复优先级：下一步优先。影响两个消息入口的记录一致性与用户体验；本轮未发现由它造成重复下单、资金变化或越权。

### 复现步骤

1. 创建独立测试用户和商家／医生会话，正常打开消息页。
2. 拦截该会话发送消息的 POST，但先向真实后端转发。
3. 后端返回成功，消息已持久化；随后中止向浏览器返回的响应。
4. 页面提示失败，输入框仍保留原文。
5. 通过独立 API 查询确认该消息已经存在一次。
6. 用户点击发送重试。
7. 查询发现两条内容相同、ID 不同的消息。

### 最终全量的实证

| 入口 | 会话 ID | 消息 ID | 两次写入时间（Asia/Shanghai） |
|---|---:|---|---|
| 商家消息 | 95 | 777、778 | 20:05:13.972441、20:05:14.087536 |
| 医生咨询 | 161 | 347、348 | 20:05:22.660917、20:05:22.783937 |

第二次全量复核再次得到商家会话 112 的消息 834／835，咨询会话 166 的消息 396／397。商家问题共四次复现，咨询问题共三次复现。两次全量的截图／trace 分别保存在 `browser-final/` 和 `browser-final-confirmation/` 下对应中文测试目录；JSON 中保留相同失败断言。

### 原因证据

- 两个前端发送函数均只提交 `{ body }`；仅在获得完整成功响应后清空草稿。失败路径保留草稿，用户重试会再次 POST。
- 两套后端发送协议没有客户端消息 ID／幂等键，发送逻辑每次插入新消息。行锁只能串行化并发写入，不能判断后一个请求是否是重试。
- 订单已有稳定幂等键，发送消息没有，所以同类网络异常下表现不同。

### 建议修复方案（本轮未实施）

为每次逻辑发送生成稳定 `clientMessageId`，重试保留同一 ID；后端以“会话＋发送者＋客户端消息 ID”建立唯一约束，在事务内返回既有消息，不重复插入。新增逻辑发送才生成新 ID。两个消息域分别实现，不混用医疗和订单表。

前端把“确定未发送”和“结果待确认”区分开来，必要时重新拉取并按客户端 ID 对账。**不能直接按文本去重**：用户有权在不同时间主动发两条相同文本。

修复验收：保留本轮两条失败用例，使其通过；再补并发重发、刷新后重试、相同内容但不同客户端 ID 两次正常发送的验证。
