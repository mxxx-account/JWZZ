# 登录与医生首页问题排查记录

日期：2026-11-06。范围：登录/注册、医生授权报告首页、双角色导航。测试只使用虚构账号及非真实体检值。

## 1. 医生收到授权后，已打开的首页不显示新报告

**确认的原因**：后端 `GET /api/doctor/reports` 使用当前医生 ID 与 `report_access_grant.revoked_at IS NULL` 查询，授权关系是持久化的；浏览器回归证明“先授权，后登录医生”能显示该报告。原医生首页只在首次加载时获取报告，之后的定时任务仅发送在线心跳。若医生首页一直开着，用户随后授权，该页持有的 `reports` 状态不会更新，除非手动点“刷新授权列表”或重新进入。

**修复**：医生首页在首次加载外，每 8 秒及窗口重新获得焦点时同步授权报告和咨询列表；两项请求分别处理，一项失败不清空另一项已成功加载的数据。手动刷新按钮保留。

**验证**：端到端用例先让医生登录并保持首页打开，用户再创建报告并输入该医生邮箱授权；断言原本不存在的报告卡片在 20 秒内出现在已打开的医生首页。实际 3 条浏览器测试全部通过，其中该用例约 9.5 秒完成。若用户登录的是另一位医生，或该报告授权已撤销，则按权限设计不会显示，需核对授权邮箱与当前医生邮箱是否一致。

**后续流程变更**：医生首页现已改为“待咨询”，不再仅凭授权显示报告。用户必须在授权后提交咨询，首页才会显示报告与附带消息；医生接受后卡片移出待咨询并在消息页出现会话。最新行为与测试见[待咨询验收记录](doctor-pending-acceptance.md)。

## 2. 医生登录要连续点击多次

**代码中确认的缺陷路径**：旧登录页在登录及 `/auth/me` 成功后使用客户端 `router.push`；新医生页立刻独立读取 `/auth/me`、在线心跳、授权报告和咨询，并把整串异步操作放在同一个 `.catch(() => router.replace('/'))` 中。因此**即使身份认证成功**，只要心跳或后续列表请求临时失败，页面也会被当成未登录送回入口，看起来像第一次“登录没成功”。这条路径由旧代码结构可直接确认；没有用户当时的网络日志，不能断言每一次多点登录都由它触发。

**修复**：登录成功、确认账号实际角色与所选身份一致后，用 `window.location.replace` 完成一次明确跳转；医生页只在 `/auth/me` 失败时返回登录，心跳失败单独容错，报告/咨询分别加载并显示各自错误。若所选身份与账号角色不同，会退出错误会话并提示切换身份，不会假装登录成功。

**验证**：浏览器用例使用新医生账号退出后，只点击一次“登录”即进入医生首页；另一个用例为在线心跳接口故意返回 503，验证成功登录后仍停留医生首页。前者验证点击次数，后者覆盖旧代码会误重定向的故障路径。

## 实际运行结果

- `mvn -o test`：12 项中 11 项通过，1 项需显式配置真实数据库的可选集成测试跳过；无失败。
- `npm run typecheck`：通过。
- `npm run test:e2e`：3 条浏览器流程通过，包括患者报告授权与双端消息、医生姓名/科室注册及单次登录（心跳故障注入）、医生首页已打开时自动收到新授权。
- `verify_stage2.ps1`、`verify_stage3.ps1`、`verify_stage4.ps1`、`verify_stage5.ps1`、`verify_messages.ps1`：本地 MySQL 环境全部通过。

这些结果证明修复覆盖所列场景；没有旧操作时的网络抓包或日志，因此“用户此前每次需要点击三遍”的确切触发次数与网络条件无法追溯。

## 3. 统一导航

旧用户/医生首页的品牌链接指向公开入口 `/`，所以点击“见微知著”会离开已登录首页。现共用顶部常驻导航，品牌字样和“首页”均链接到当前角色首页，“消息”链接到对应角色的消息页；只有“退出登录”调用登出接口。用户和医生页面均通过浏览器回归验证品牌链接不会回到登录入口。

## 注册与安全边界

V6 迁移为 `app_user` 增加姓名字段；注册要求邮箱、姓名、至少 12 位密码、用户/医生身份；医生还需选科室并建立 `doctor_profile`。既有账号保留，旧账号缺少姓名时界面回退显示邮箱；内置演示医生在开发启动时补齐虚构姓名。

**医生自行注册仅在 `dev` 配置开启**，默认配置禁用；当前没有身份证明、执业资质审核，角色是自选的**演示身份**，不得把它用于真实医疗服务或真实患者资料。正式开放前必须增加审核流程及已验证状态，不能直接把公开注册结果当成真实医生资格。
