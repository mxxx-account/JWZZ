# 技术难点与取舍（面试说明）

1. **先做可解释规则，不把旧 DKD 模型硬接进平台。** 当前可用输入是血压、血糖、血脂及测量条件，旧 NHANES 模型的特征、人群与标签定义不同。强行接入会产生无法解释的“患病概率”。所以当前报告只保存原始值、单位转换、适用条件、规则来源和版本，并明确“待临床审核”。代价是暂不提供疾病预测。
2. **权限以报告授权为核心。** 医生目录展示不等于访问权。用户按报告授权，咨询定向发送给该医生；每次医生读写都通过 `report_access_grant.revoked_at IS NULL` 过滤。撤销后历史仍保留在用户侧，医生侧立即不可见。代价是查询需要联表，不能简单把授权结果长期缓存。
3. **并发控制交给数据库约束。** 报告生成用 `(user_id,idempotency_key)` 唯一索引并在冲突时读回原快照；接单是 `OPEN → CLAIMED` 的条件更新。单实例 Java 锁无法跨进程保证正确性。已有 8 路并发 HTTP 测试验证同一报告 ID、单人接单。
4. **事务保证“会话与首条消息”一致。** 咨询创建、第一条消息同事务；医生回复的状态更新和消息写入同事务。可选 MySQL 集成测试通过故意使用不存在的发送者 ID 触发外键错误，验证同事务创建的咨询也回滚；随后验证正常路径两表一起提交。它验证了存储层的真实回滚，不等于已覆盖所有网络/进程故障。
5. **轮询优先于 WebSocket。** 当前用户少、异步演示性质明确，约 8 秒轮询加 30 秒医生心跳更容易完成和测试。代价是延迟、重复查询以及高并发时的连接与数据库负担；真实在线诊疗还需要推送、离线通知和排班等能力。
6. **Redis 只用于低敏感共享状态。** 公开指标目录缓存、Lua 原子限流；不把用户报告放进公共缓存。Redis 不可用时降级为本机限流，跨实例语义会丢失，因此不能宣称生产级分布式限流。
7. **选择单体而非微服务。** 项目业务与团队规模尚小，Spring Boot 单体加 MySQL/Redis 更容易保持授权事务与调试清晰。未来若有大量实时会话，可在明确性能指标和边界后拆分消息服务。
8. **已定位的性能问题。** 在并发 20、每接口 400 次请求的本机测试中，60 份报告的列表约 380 次/秒、p95 79 ms，明显慢于 1 份报告时的约 3405 次/秒、p95 15 ms。代码中 `ownedBy` 无分页且逐份解析 JSON；这是合理的瓶颈解释，但尚未做 SQL/CPU profiler 来精确分摊耗时。下一步应先做分页、响应裁剪和测量，而不是盲目加线程池。
9. **商家库存的现阶段边界。** 第二阶段把商品模板、店铺 SKU、可售／预留库存和应用层只追加的调整流水分开。商家调整可售库存时在 MySQL 事务中锁定该 SKU 的库存行，再写入目标数量和变动前后流水，避免管理端并发修改造成流水与库存不一致。预置 SKU 默认零库存、未上架；商家后台的“上架”尚不使草稿店铺进入用户搜索。第四阶段已补齐订单预留、取消回补与接单结转。
10. **第三阶段搜索与购物车。** 搜索在 MySQL 中只读取演示营业中、已上架且可售库存大于 0 的 SKU，不用缓存中的旧库存决定是否可加入购物车。购物车限制单店：写入事务先锁当前用户行，再检查已有店铺和商品当前库存，避免两个并发请求分别加入不同店铺。购物车不预留库存，商品下架或缺货仍保留条目但标记不可购买；第四阶段下单时重新校验并预留。当前默认按最新 SKU 排序而非真实销量，也不提供距离排序。

# 第四阶段：订单预留与状态机

下单使用 MySQL 事务和库存行锁，不靠 Redis 计数做最终库存真相。先按 SKU 排序锁定库存行，再统一核对、预留、写入订单和快照、清空购物车；事务失败会整体回滚。`available` 表示可售，`reserved` 表示已被待支付／待接单订单占用。取消或超时把预留回补可售，商家接单把预留转为已售。订单行锁与状态条件更新保证重复操作不会二次释放；用户行锁加 `(user_id, idempotency_key)` 唯一索引保证并发重复提交只有一单。代价是热点 SKU 下单会排队，但相较为面试演示项目引入消息队列与分布式库存，当前方案更容易证明一致性。

支付是模拟状态流转，没有支付渠道回调、退款或对账；已模拟支付的订单不能由用户直接取消。后台每 30 秒轮询过期待支付订单，可恢复但不是精确到秒的关单。生产化需要支付回调验签、可靠延迟任务／补偿扫描、退款及订单履约等能力。

# 第五阶段：订单消息隔离与压测

商家消息没有复用医生咨询表：会话只外键关联演示订单，并由订单用户或店铺商家访问；查询路径中不出现医疗报告。代价是两套聊天接口与页面有重复代码，但边界清晰，能明确证明商家不会通过消息接口拿到报告。每订单唯一会话加订单行锁保证并发发起只创建一份首消息；发送与已读按会话行锁串行化，换取无丢消息和一致的未读游标。当前使用 8 秒轮询、列表最多 100 个会话、详情最近 200 条；若业务量增长，应先加历史游标分页、未读聚合和推送方案，再考虑拆服务。

单机有界压测中，同会话并发写入 30 条的 p95 为 33.6 ms、约 376 次/秒，读取列表/详情 p95 为 12.1～14.4 ms。行锁和事务写入是合理解释，但尚未做 profiler，不能断言它们是唯一瓶颈或推导生产容量。压测没有引入线程池或分布式锁：MySQL 约束与事务仍是消息一致性的事实源。
