# 消息页未读标号未及时消失：问题记录

记录日期：2026-11-06。范围：患者和医生共用的消息页 `web/src/app/messages/chat-workspace.tsx`。本记录只讨论左侧未读标号的刷新，不改变消息是否已送达或后端已读游标的含义。

## 复现条件与现象

1. 账号 A 向账号 B 的某个会话发送消息，B 保持消息页打开、当前查看另一会话。
2. B 左侧的新会话出现红色未读数量；点击该会话，右侧能看到新消息。
3. 修改前：红色数量继续显示。B 再发送消息、接单，或者等待下一次约 8 秒轮询，数量才可能消失。

患者和医生都使用同一消息页组件，所以两种角色会遇到相同的前端状态问题。后端的 `POST /api/messages/conversations/{id}/read` 会把该角色的已读消息 ID 更新到 `consultation_request`，数据库并非等到发送消息才标记已读。

## 根因定位

打开会话的 `refreshDetail(id)` 依次获取详情、调用已读接口，但此前**没有更新左侧 `items` 列表的 `unreadCount`**。左侧红色标号和顶部总数都从 `items` 渲染，不从详情或数据库实时读取。因此已读请求成功后，浏览器仍显示旧列表快照。发送消息和接单路径会额外执行 `refreshList()`，所以这两个动作看起来“顺带修好了”未读标号。已经选中的会话被再次点击时，`activeId` 不变，依赖 `activeId` 的 effect 也不会重跑，进一步放大该现象。

数据流（修改前）：点击会话 → `GET` 详情 → `POST` 已读 → 右侧详情更新；左侧 `items` 未变 → 红点保留，直到其他操作或轮询刷新列表。

## 修复方案

- 已读接口**成功返回后**，把该会话在 `items` 中的 `unreadCount` 设为 0，并同步右侧详情摘要。这样左侧标号与顶部总数立即按已确认的后端状态更新；请求失败时不假装已读。
- 对“再次点击当前已选中的会话”显式调用 `refreshDetail(id)`，不依赖 `activeId` 变化触发 effect，并为请求失败显示提示。
- 不更改后端游标 SQL：它已用 `MAX(message.id)` 及 `GREATEST` 保证同一会话的已读游标不倒退。8 秒轮询继续用于接收新消息，而不是用户点击已读后的必要步骤。

## 验证与边界

浏览器端到端用例在同一真实 MySQL 后端中创建患者、报告、授权和两条咨询：医生停留在第一条会话，等待第二条会话显示红色 `1`，**只点击第二条、不发送消息**，断言该会话红色数量消失。还覆盖手动输入医生邮箱授权和筛选下拉框。`npm run typecheck` 与后端 `mvn -o test` 已通过。

测试构建过程中曾出现两个测试断言问题，并非产品缺陷：第一次在页面异步跳转完成前读取 URL，得到 `null` 会话 ID，已改为先等待目标 URL；第二次错误地要求医生账号的**全部**未读归零，但该共享演示账号还有此前测试留下的其他会话，已改为只断言本次点击的会话标号消失。调整后执行 `npm run test:e2e`：1 条完整用例通过，约 21 秒；点击后本次会话的红色未读数消失，过程中没有发送消息。

剩余边界：这不是 WebSocket 推送；新消息仍可能在下一次轮询才出现。若已读请求失败，红点会保留或在后续列表刷新中重新显示，避免把失败误报为已读。测试账号为虚构演示账号，不能用于真实患者资料。
