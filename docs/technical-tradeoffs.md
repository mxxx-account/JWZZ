# 技术难点与取舍（面试说明）

1. **先做可解释规则，不把旧 DKD 模型硬接进平台。** 当前可用输入是血压、血糖、血脂及测量条件，旧 NHANES 模型的特征、人群与标签定义不同。强行接入会产生无法解释的“患病概率”。所以当前报告只保存原始值、单位转换、适用条件、规则来源和版本，并明确“待临床审核”。代价是暂不提供疾病预测。
2. **权限以报告授权为核心。** 医生目录展示不等于访问权。用户按报告授权，咨询定向发送给该医生；每次医生读写都通过 `report_access_grant.revoked_at IS NULL` 过滤。撤销后历史仍保留在用户侧，医生侧立即不可见。代价是查询需要联表，不能简单把授权结果长期缓存。
3. **并发控制交给数据库约束。** 报告生成用 `(user_id,idempotency_key)` 唯一索引并在冲突时读回原快照；接单是 `OPEN → CLAIMED` 的条件更新。单实例 Java 锁无法跨进程保证正确性。已有 8 路并发 HTTP 测试验证同一报告 ID、单人接单。
4. **事务保证“会话与首条消息”一致。** 咨询创建、第一条消息同事务；医生回复的状态更新和消息写入同事务。可选 MySQL 集成测试通过故意使用不存在的发送者 ID 触发外键错误，验证同事务创建的咨询也回滚；随后验证正常路径两表一起提交。它验证了存储层的真实回滚，不等于已覆盖所有网络/进程故障。
5. **轮询优先于 WebSocket。** 当前用户少、异步演示性质明确，约 8 秒轮询加 30 秒医生心跳更容易完成和测试。代价是延迟、重复查询以及高并发时的连接与数据库负担；真实在线诊疗还需要推送、离线通知和排班等能力。
6. **Redis 只用于低敏感共享状态。** 公开指标目录缓存、Lua 原子限流；不把用户报告放进公共缓存。Redis 不可用时降级为本机限流，跨实例语义会丢失，因此不能宣称生产级分布式限流。
7. **选择单体而非微服务。** 项目业务与团队规模尚小，Spring Boot 单体加 MySQL/Redis 更容易保持授权事务与调试清晰。未来若有大量实时会话，可在明确性能指标和边界后拆分消息服务。
8. **已定位的性能问题。** 在并发 20、每接口 400 次请求的本机测试中，60 份报告的列表约 380 次/秒、p95 79 ms，明显慢于 1 份报告时的约 3405 次/秒、p95 15 ms。代码中 `ownedBy` 无分页且逐份解析 JSON；这是合理的瓶颈解释，但尚未做 SQL/CPU profiler 来精确分摊耗时。下一步应先做分页、响应裁剪和测量，而不是盲目加线程池。
9. **商家库存的现阶段边界。** 第二阶段把商品模板、店铺 SKU、可售／预留库存和应用层只追加的调整流水分开。商家调整可售库存时在 MySQL 事务中锁定该 SKU 的库存行，再写入目标数量和变动前后流水，避免管理端并发修改造成流水与库存不一致。预置 SKU 默认零库存、未上架；商家后台的“上架”尚不使草稿店铺进入用户搜索。订单预留、支付结转、取消回补、幂等与并发防超卖属于第四阶段，当前不能宣称已经实现。
