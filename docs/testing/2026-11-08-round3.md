## 故障与恢复记录

### Redis

断开测试 Redis 连接后，公开指标目录仍为 200 且内容一致；新测试商家发送前 60 条消息成功，第 61 条 429。恢复连接后目录与发送均恢复。

Redis 与内存回退的计数桶独立；本测试不证明切换前后严格合并计数，也不证明多实例降级限流一致。该限制仍应保留在架构说明中。

### 数据库

断开 8082 专属数据库代理连接后，指标读取返回 500；健康接口仍返回 200，只能解释为进程存活，不能作为数据库就绪探针。Node HTTP 探针曾观察到写入消息返回 HTTP 200、空响应，记录为 **Q3-OBS-001 待复核异常**，不能直接认定浏览器端数据丢失。

恢复后确认故障期间消息未持久化；使用同一个客户端消息 ID 重试两次，数据库只保存一条。连接池恢复，无需重启该测试后端。

最初一次夹具错误地向库存已全部预留的商品再加入购物车，返回 404；删除该无关准备操作后继续。后续原始断言要求写错误为 5xx 时失败，进一步检查确认是 200 空响应，**保留为协议缺陷，不改成全部故障测试通过**。对应 `resilience-attempt*.log/json` 保留排查过程。

## 新缺陷与建议

### Q3-OBS-001：HTTP 探针与浏览器的错误响应观测不一致（未确证产品缺陷）

故障代理关闭时，消息未写入，但 POST 返回 200 空内容。预期为明确的 5xx（例如 503）和可解释错误。根因尚不能仅凭 HTTP 结果断言，应检查事务异常、错误分派与统一异常处理；不能先认定写事务已成功。

**浏览器最终实证：两项均通过。** 对咨询和商家接口分别等待初始化已读请求完成，再注入故障，并明确等待实际发送 POST 的响应。咨询发送返回 500、响应长度 129；商家发送返回 500、长度 134。两者均保留草稿，恢复后确认该测试文本持久化数量为 0。故障过程结束后撤销授权或取消订单／暂停店铺。

因此本轮没有证明“草稿丢失”，不将假设写成已确认事实。Node 探针与浏览器结果差异还需隔离 HTTP 客户端／请求时序再核对，不能仅凭它断定唯一服务端根因。Node 检查仍保留 `errorContractPassed=false` 与退出码 1，不覆盖原始异常观测。

首次浏览器夹具未等待初始化已读与连接池恢复，清理读取曾为 500，掩盖了原断言；修正等待条件后两种消息通过。首轮失败 trace 保留在 `fault-browser-first/`，它不是已确认草稿丢失证据。

防御性建议：统一基础设施异常响应协议，不泄露连接凭据；前端可验证写成功响应结构。结果不明时保留待确认消息和幂等 ID，恢复后对账；需要后续单独设计验证，非本轮已实施修复。

### Q3-BUG-002：商家接单后库存板块未刷新

接单后接口显示预留 0，商品卡片持续显示预留 1；订单列表正确变成“已接单”。两次复现，非数据库库存错误。

源码证据：OrderPanel 接单只刷新自身订单状态；ProductPanel 独立维护 products，没有收到库存失效通知。建议通过父级刷新版本或共享查询失效机制，在接单成功后重新读取商品库存。不能只把页面上的数字手工减一。

## 稳定性采样说明

测试脚本 `scripts/quality_resilience.mjs`，目标 30 分钟，每两秒同时读取健康、公开目录、指标历史、会话列表、会话详情五个接口，每分钟采样 JVM 的 CPU 累计时间、工作集、私有内存与句柄数。故障阶段结束后才开始计时，稳定性阶段没有再次注入故障。

期间同机运行了生产副本构建与独立 8083 验收，也运行了 8082 的五套接口功能脚本；因此是开发机有限背景活动下的低负载观察，不是严格独占硬件基准或容量上限。

### 最终稳定性结果

- 实际计时 1800 秒，约 20:44:04～21:14:04，4500 次请求（约 2.5 次/秒），非 200 为 0，整体 p95 17.2ms。
- 每分钟资源采样共 30 次，第 0～29 分钟：工作集首 317.0MiB、末 225.1MiB，范围 225.1～337.3MiB；私有内存首 425.6MiB、末 464.2MiB；句柄 984→974；累计 CPU 时间增加 37.56 秒。不是 JVM 堆 profiler，不能据此证明不存在内存泄漏。
- 收尾前两个测试后端各有 4 条本库连接，与池上限一致；未量测完整连接峰值，不能声称做了全面连接泄漏分析。
- 稳定性读取观察通过；整个 resilience 脚本最终退出 1，因为保留了 HTTP 响应协议的待复核结果，且商家闲置 30 分钟后会话失效，自动暂停店铺清理返回 401。不能把脚本退出码改写为 0。
